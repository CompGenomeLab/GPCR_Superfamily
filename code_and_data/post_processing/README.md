# Search-result post-processing and homolog-clade extraction

Full search outputs, exploratory alignments/trees, ordered files, and interactive line plots are distributed through the Zenodo archive described in the [top-level README](../../README.md#data-on-zenodo). This folder contains the scripts that organize broad search results for inspection and extract the manually curated homolog sets used downstream.

## Upstream inputs

Inputs are generated by `homolog_search_pipeline/` under:

```text
search_results/<family>/
```

HMMER searches provide two alignment/tree sets:

- Complete sequences: `*_db_FAMSA_gt0.1.*`
- HMM regions: `*_db_hmmregions_FAMSA_gt0.1.*`

MMseqs2 searches provide the complete-sequence alignment/tree and a 15-column `.m8` score table.

## Step 1 - Order trees by search score

Scripts:

- `tree_fasta_order_and_line_plot.sh`
- `tree_order_by_hmm.py`
- `fasta_order_by_tree.py`
- `line_plot_hmm_and_index_treeorder.py`

The SLURM array script processes every configured GPCR family, STE2, the G-protein subunits, and the TBP/RBP1 controls. Each family is paired with either `hmm` or `m8`, matching the search method used upstream.

For HMMER searches, the workflow orders both the complete-sequence and HMM-region results. For MMseqs2 searches, it orders the complete-sequence results:

1. Reads HMMER scores or MMseqs2 bit scores.
2. Roots the exploratory tree using the lowest-scoring matched leaf.
3. Recursively compares sister-clade mean scores and places the higher-scoring clade first.
4. Rewrites the matching FASTA in the resulting tree-leaf order.
5. Produces an interactive line plot of normalized score and normalized original
   search-result index along the ordered leaves. The x-axis contains the
   tree-ordered sequence IDs with tick labels hidden. The index metric comes from
   the zero-based HMMER/MMseqs2 hit-list row (not from the tree). Hover text uses
   the retained plot convention and reports the metric label, sequence ID, and
   plotted value. The four legend labels are `Score_smoothed`,
   `Normalized_Index_smoothed`, `Score`, and `Normalized_Index`.

This arrangement places high-scoring regions together and makes abrupt score declines easier to compare with sequence-pattern changes in the MSA.

Run after sourcing `config/paths.sh` and setting an array range matching the 23 configured entries:

```bash
sbatch code_and_data/post_processing/tree_fasta_order_and_line_plot.sh
```

Important outputs:

| Pattern | Contents |
|---|---|
| `*_hmmordered.tree` | HMMER-score-ordered tree |
| `*_m8ordered.tree` | MMseqs2-score-ordered tree |
| `*_treeordered.fasta` | Alignment written in ordered-tree leaf order |
| `*_score_lineplot.html` | Interactive score/search-index diagnostic displayed in tree-leaf order |

## Step 2 - Inspect and define homologous clades

The ordered tree, matching tree-ordered MSA, and score line plot are inspected together. A retained homologous region is expected to satisfy three criteria:

1. Its sequences score more strongly than more distant matches.
2. It shows a distinguishable sequence pattern in the ordered MSA.
3. The corresponding sequences form a coherent clade in the exploratory tree.

The manually selected boundary leaves and any explicitly excluded subclades are recorded in the `gene_boundaries` dictionary in `identify_gene_clade.py`.

## Step 3 - Extract curated homologs and prune trees

Script: `identify_gene_clade.py`

For each configured entry, the script:

1. Loads the selected HMM-region, complete-sequence, or MMseqs2-ordered tree.
2. Finds the most recent common ancestor of each boundary pair.
3. Combines retained clades and subtracts boundaries marked with `-1`.
4. Writes the corresponding sequences from the tree-ordered FASTA.
5. Prunes the ordered tree to the retained sequence set.

For HMMER searches, the result that gives clearer separation of the target family is selected in `gene_boundaries`: `hmmregion: 1` uses the HMM-region files and `hmmregion: 0` uses the complete-sequence files. MMseqs2 searches use the m8-ordered complete-sequence files.

The Zenodo archive preserves these files inside each family's search-results
folder; users do not need to copy them into separate staging directories. Set
the root of the downloaded search results before running the extraction:

```bash
export GPCR_ZENODO_DIR=/path/to/zenodo_data  # omit when unpacked inside the repository
source config/paths.sh
```

The resolver reads the same directory style created by the search scripts:

```text
search_results/<family>/
```

For MMseqs2 searches it uses the family directory, such as
`search_results/GPR1_YEAST/`. Each directory must contain the matching ordered
tree and tree-ordered FASTA described above. The older flat
`hmmorder_trees/` and `treeorder_msa/` layout remains a fallback for retained
local analyses, but it is not required for the Zenodo release.

If a future archive uses a different family-folder name, add a
`search_folders` list for that family in `identify_gene_clade.py`; explicit
`tree` and `fasta` paths are also supported for exceptional cases.

Run with:

```bash
python code_and_data/post_processing/identify_gene_clade.py
```

Main outputs:

| Location | Contents |
|---|---|
| `extracted_clades/alignments/<family>_*_treeordered_extracted_clade.fasta` | Extracted clade alignment, preserving the source alignment columns and tree order |
| `extracted_clades/trees/*_extracted_clade.tree` | Ordered tree pruned to the extracted clade |

Class B1 and Class B2 are both reconstructed from the retained broad Class B
search. This shared Class B/secretin-family HMM search is intentional. Class B2
is an exception consisting of one included clade and one excluded subclade.
Vomeronasal1 is likewise extracted as a clade from the retained Class T
(Taste-2 receptor) search, while Class T/Taste-2 uses its own boundary in that
same tree.
The `search_name` entries encode these cross-family search sources explicitly.
Both definitions reproduce the retained extracted FASTAs exactly, including
sequence order.

Shared search inputs are read-only. `output_name` gives Class B1 its own gene
alignment and extracted-tree names, while Class B2, Class T, and Vomeronasal1 use their
family names. A complete run therefore cannot overwrite one family's output
with another family's result even when both read the same alignment and tree.

## Dependencies

- Python 3
- ete3
- Biopython
- NumPy
- pandas
- Plotly

The extracted FASTAs pass to [`family_processing/`](../family_processing/README.md), where accessions are expanded, E-value/length filtered, clustered, and aligned family by family.
